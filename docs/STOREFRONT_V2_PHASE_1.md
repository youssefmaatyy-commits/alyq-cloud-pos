# ALYQ Cloud POS — Storefront V2 Phase 1 final report

**Date:** 24 September 2026\
**Status:** Phase 1 implemented and validated as an **opt-in public presentation**. Phase 2 has not started.\
**Open:** `#/store/v2` · `#/store/v2/products` · `#/store/v2/products/:slug-or-id`

## Delivery and architecture

1. **Scope.** V2 is a new, original, minimal, mobile-first storefront presentation, not a replacement commerce system. It reads the existing published shop data and leaves checkout/order authority in the existing implementation.
2. **Public routing.** Added V2 home, catalogue and product detail under `#/store/v2/*` inside the public `/store` branch; unknown V2 subpaths return to the V2 home. No staff authentication is required just to browse.
3. **Legacy coexistence.** `#/store`, `#/store/products`, existing product deep links, cart, checkout, account, about, contact and tracking still use their existing routes and pages. V2-to-legacy cart navigation and legacy catalogue navigation were exercised.
4. **Provider reuse.** V2 mounts within the same `StorefrontProvider`, `StoreAccountProvider` and `StoreCartProvider`; the route chooses a V2 shell instead of `StoreLayout`, without a second cart, session or catalogue state machine.
5. **Data and service reuse.** Product/category/variant data comes through `StorefrontProvider` and `src/modules/storefront/data/storefrontCatalog.ts`; website content, orders and settings continue through `src/modules/online/data/` and the existing services/RPC contracts.
6. **Back-office and database boundary.** No V2 work changed POS/Admin behavior, inventory mutation, reservation logic, order placement, SQL, RLS or schema, and nothing was deployed. Existing unrelated dirty worktree changes—including pre-existing database files—were preserved, not reset or incorporated into this V2 implementation.
7. **Implementation map.** `src/App.tsx` registers routes; `src/modules/online/StorefrontApp.tsx` selects the shell; `src/modules/online/v2/` contains the shell, pages, product card, variant chooser, appearance/price/variant adapters, primitives and scoped CSS. Paired EN/AR strings are in `src/lib/i18n/dictionary.ts`.

## Shopper experience

8. **Design tokens.** `.store-v2` scopes layout, typography, spacing, colors, button/card shapes and responsive rules. The appearance adapter reads saved website settings and supplies contrast-aware foreground colors; it does not apply V2 tokens to POS/Admin.
9. **Languages and direction.** Existing i18n drives English LTR and Arabic RTL, including headings, labels, currency formatting, navigation, selection controls and footer. The language switch does not change a selected product's identity.
10. **Announcement bar.** Existing enabled messages, configured colors, links and timed *rotate* mode feed a compact announcement. A separate scrolling ticker animation is not implemented; see point 33.
11. **Header.** Responsive, centered brand/wordmark, configured search/account/cart entries, live cart count, desktop navigation and language control are present. Optional header controls respect saved enablement flags.
12. **Keyboard navigation and mobile drawer.** The skip link focuses the main content without changing the HashRouter route. A labelled drawer provides shop/category/info links and language switching; it traps keyboard focus, closes on Escape, restores focus/body scrolling and keeps its long navigation independently scrollable.
13. **Search.** Header search and the catalogue form use V2 catalogue query URLs; direct query-string/category/offer links can be opened without going through the home page.
14. **Homepage configuration.** Existing saved section order, visibility, titles, limits, links and imagery drive the homepage. Sections with no qualifying configured content are omitted; an all-empty configuration receives an intentional empty state.
15. **Hero.** Configured desktop/mobile slide imagery, titles, CTAs, overlay, content placement and heights are used. Multiple slides have controls and timed advance that pauses on interaction/reduced motion; no V2-specific stock photography or copied reference-site assets were added.
16. **Editorial modules.** Configured categories, campaigns, promo banners, lookbook/editorial/text-image/about, trust strip, newsletter, brands, reviews, FAQ, social gallery and contact sections render only when their relevant existing data is available.
17. **Merchandising modules.** Featured, best sellers, new arrivals, curated collection and sale sections derive from published products, actual sale history/selection and live offers; they do not fabricate a best-seller ranking, product or promotion.
18. **Product grid.** The catalogue and merchandising grids show two columns on the requested mobile widths, three at tablet and four by default on desktop. Saved desktop column count and card gap can override the desktop presentation.
19. **Product cards.** Cards share one reusable component with actual imagery, localized name/brand, advisory price, configured badges, availability, swatches, wishlist and Quick Add/options. Saved image aspect/fit, text alignment and visibility controls are applied.
20. **Wishlist and Quick Add.** Wishlist delegates to the existing account provider. Simple products can use Quick Add; products with more than one exact published variant open an explicit option chooser instead of guessing a combination.
21. **Catalogue controls.** Search, category/brand, stock/offer and price controls, sort order and URL state use the existing catalogue query. V2 price range and price sorting additionally use the same advisory promotion-aware price shown on its product cards.
22. **Product detail.** PDP includes breadcrumbs, real product/content media and thumbnails, localized descriptions, SKU, price, availability, quantity, configured content/specifications, reviews and related items. Missing media uses a labelled fallback; unpublished size-guide content is not invented.
23. **Exact variant identity.** Color and size choices come from active published variant rows, not an inferred color×size grid. Numeric sizes including `16.5`, saved letter labels such as `XS` and `One Size`, and combined color+size choices retain the selected variant UUID.
24. **Availability and selection.** Sold-out combinations remain visible but disabled; a color change clears the old size selection. Reserved quantities are reflected when available to the client; tracking-disabled and unsellable products cannot be Quick Added. Neither the UI nor the cart silently substitutes a different variant.
25. **Advisory price.** Variant overrides, live campaigns and promotions appear on cards/PDP and in V2 price filtering/sorting. These browser values are advisory; the existing server-side `place_online_order` flow still checks current stock, coupons and final price.
26. **Cart/order handoff.** V2 adds `{product_id, variant_id, quantity}` through the existing cart provider. Separate exact shelves stay separate cart lines; V2 does not decrement inventory directly, bypass reservations, create an alternate checkout or place orders itself.
27. **Footer.** Settings-backed brand description, social links, shop/information links, contact details, policy links, copyright and language switch are responsive in EN/AR. The newsletter CTA opens email; it is **not** an unimplemented subscription endpoint.
28. **States and preview SEO.** Loading, empty, retryable data-error, unavailable and not-found states are provided. V2 sets `noindex, nofollow` while it is an opt-in preview rather than the canonical shop; its metadata is cleaned up on leaving the route.

## Validation and outcome

29. **Static/build checks.** `npm run typecheck` and `npm run build` passed; `npm run lint` passed with **0 errors, 34 warnings** in the worktree. `git diff --check` passed. No warning was misreported as an error-free lint run.
30. **Logic and DOM E2E.** `npm run test` passed **46/46 logic suites**, including **7/7 focused V2 logic tests**. The full `npm run test:e2e` passed **22/22 suites**; after the skip-link fix the focused V2 E2E reran and passed **28 DOM checks** for data, routing, EN/AR, keyboard focus, sold-out options, exact UUID cart lines, override pricing and legacy handoff. jsdom is not treated as visual proof.
31. **Real-browser V2 acceptance.** Chromium checked home, catalogue and PDP at **320, 360, 375, 390, 414, 768, 1024, 1280, 1440 and 1920 px**, in both **EN/LTR and AR/RTL**: **60/60** page cases. Additional fixture-based exact-variant PDP checks passed **20/20** language/width cases, with expanded card chooser samples in both languages at 320, 390, 768, 1440 and 1920 px. Tests checked header actions/centering, the keyboard skip link's focus and unchanged route, mobile drawer fit/scroll/Escape/body unlock, loaded images, visible control bounds, grid columns, headings, footer reachability, horizontally scrollable category chips, absence of page overflow and browser console/network errors. A persisted palette, five desktop columns, square imagery and hidden card controls/section were verified after reload. Representative screenshots were inspected and live in ignored `coverage/visual-v2/` during the test session.
32. **Legacy/POS/Admin assurance.** The separate rendered acceptance suite passed **80 screens**, including legacy storefront, Admin pages/theme reloading and EN/AR POS layout/scrolling at crowded desktop and tablet sizes. The full logic/E2E suites also cover existing POS, Admin and online flows. These checks found no regression attributable to V2; they are not a claim of exhaustive production coverage.

## Boundaries and next approval

33. **Known Phase 1 limitations.** V2 is intentionally opt-in, not the canonical `/store` route; checkout/account/about/contact/tracking remain legacy pages. A universal size chart is not manufactured when product size information is absent. The announcement's existing `scroll` mode displays a message without a scrolling ticker. Newsletter actions use `mailto:` only. Browser tests used the isolated demo catalogue plus test-only variants, not a live production Supabase deployment; no formal accessibility certification or production-order test is claimed.
34. **Future settings support / stop point.** `appearance.ts` already exposes typed, *non-persisted* override hooks for a mobile logo, header/footer/button/badge/border/hero colors, text, logo height and sticky header. A future, explicitly approved phase can add admin persistence/preview for those controls, consider ticker parity and decide whether to move other shopper pages to V2. None of that work, any database migration, or **Phase 2** was started here.
