# ALYQ Cloud POS — Storefront V2 Phase 3 final report

**Date:** 24 September 2026 (Africa/Cairo)

**Outcome:** Phase 3's opt-in shopper journey is implemented and validated locally. This is **not** a production launch or a claim that live Supabase checkout was exercised.

**Entry:** `#/store/v2` · **Canonical/legacy entry remains:** `#/store`.

## Scope and ownership

1. **Phase 3 outcome.** The existing V2 home, catalogue and PDP now lead through V2 bag, checkout, confirmation, private tracking, account, About and Contact pages. This final pass corrected historical reorder orderability, partial-reorder feedback and catalogue-loading races; it did not start Phase 4.
2. **Ten opt-in public routes.** `src/App.tsx` registers `#/store/v2`, `/products`, `/products/:key`, `/cart`, `/checkout`, `/confirmation`, `/track`, `/account`, `/about` and `/contact` beneath that prefix. `:key` accepts the existing product slug or ID. An unknown V2 subroute returns to the V2 home, not to a staff screen.
3. **Legacy separation.** `#/store` still shows the original storefront; its existing product, cart, checkout, confirmation, tracking, account, About and Contact routes remain intact. `StorefrontApp.tsx` selects the V2 shell **only** for `/store/v2` paths. No default-route switch, redirect from legacy, or Phase 4 cutover occurred.
4. **One set of providers.** Both shop presentations mount under the existing `StorefrontProvider → StoreAccountProvider → StoreCartProvider` tree. V2 adds presentation and client-side journey guards, not a second catalogue, cart, shopper account, coupon calculator, stock ledger or order writer.
5. **Order authority.** Catalogue visibility, current stock/variant checks and price previews are helpful browser information. The existing `StoreCartProvider.checkout()` and online-orders repository place the order; in live mode the existing `place_online_order` contract is authoritative for accepted items, availability, zones, discounts and totals. V2 never marks a payment paid or adjusts inventory directly.
6. **Demo versus live repositories.** The tested browser ran **demo mode** with independent localStorage-backed catalogues, orders, reservations, settings and accounts. Live mode selects the existing Supabase repositories and public storefront reads when configured. A passing local demo checkout is not proof of a production order, live policy configuration or a successfully deployed migration.
7. **Phase 2 continuity.** V2 still consumes the shared saved website content and the Phase 2 presentation-only `storefront_v2` appearance overrides, bilingual Studio settings, social channels and safe WhatsApp links. This pass did not recreate or replace the customization Studio, ticker, product images, Admin editor or POS theme.
8. **Implementation boundary.** Routes/shell are in `src/App.tsx`, `src/modules/online/StorefrontApp.tsx` and `src/modules/online/v2/`; bilingual strings are in `src/lib/i18n/dictionary.ts`. The focused reorder guard lives in `v2/journeyModel.ts`, while `v2/StorefrontV2Account.tsx` delegates additions to the shared cart. No Phase 3 SQL/RLS/RPC or backend service was introduced.

## Shopper journey and safety

9. **V2 shell and navigation.** The existing V2 header, announcement, search, account/bag links, category navigation, drawer, footer, skip link and scoped `.store-v2` styles remain consistent from browsing through the last journey page; an optional hidden header icon never removes the underlying route.
10. **Catalogue discovery.** Search, category, colour, numeric/letter size, brand, availability, offer and sorting options use published data and URL-backed query state. Browser reload retains filters. A no-result query shows an intentional empty state rather than an invented product.
11. **Product selection.** The PDP presents published product content, actual variant rows, size guidance when configured, availability and related merchandise. Selecting Gold/17 cannot resolve to Silver/17; sold-out Gold/18 cannot be added merely because another size is available.
12. **Real media and keyboard gallery.** The PDP uses stored images and a labelled fallback, not new stock photography. In Chromium, the size guide opened, the image lightbox announced a dialog, arrow keys moved through images and Escape returned focus to its trigger.
13. **Bag line identity.** A cart line preserves `product_id`, the **exact** `variant_id` UUID or `null` for a simple product, and quantity. V2 shows SKU/variant detail, limits quantity to the actual shelf, and delegates add/increase/decrease/remove/clear to `StoreCartProvider`.
14. **Current orderability.** Published and active status, current variant ownership/activity, stock tracking, on-hand stock and known reservations constrain V2 add/reorder. A tracking-disabled product is **not orderable through V2 checkout**; a `null` availability from disabled tracking is not permission to reorder it.
15. **Persisted stale bags.** After a successful catalogue load, the shared cart removes saved lines that name missing or invalid products/variants and V2 shows a dismissible notice. It does not silently pick a replacement variant. The Chromium test seeded both a nonexistent product and wrong-product variant and observed the pruned empty bag.
16. **Advisory totals.** Bag and checkout show the shared provider's preview of subtotal, discounts, delivery and total with a visible advisory label and loading indicator. They do not send a browser-calculated final amount as an order authority.
17. **Coupon handling.** Applying/removing a code invokes the existing precheck; eligibility and preview are explicitly provisional. The settled DOM journey checked `WELCOME10` and a selected Cairo fee **before** placement and compared the displayed estimated total with the subsequent authoritative demo order snapshot.
18. **Fulfilment.** Pickup and configured delivery zones share the legacy fulfilment settings. Zone selection, shipping fee, minimum-order check and address rules feed the existing checkout path; changing payment or zone does not freeze a stale order-form callback.
19. **Contact and addresses.** Guest checkout takes name, Egyptian phone and an inline delivery address. A signed-in shopper can reuse a saved, browser-local address; checkout snapshots the actual address into the order, rather than depending on future profile edits.
20. **Payment selection.** COD and InstaPay appear only when enabled in saved shop settings. The checkout shows the relevant instructions and does not invent another processor, proof inbox or transaction status.
21. **Form guards.** Required name/phone, address, area, zone, minimum and stock/fulfilment availability have bilingual feedback. An empty contact cannot place an order; these front-end checks are not represented as the server's final acceptance decision.
22. **Safe submission.** A synchronous pending guard prevents a rapid double click before React disables the button. The cart provider's existing idempotency reference and repository retain order authority; the DOM test clicked twice and observed **one** COD order, not two.
23. **COD result.** Pickup/COD produced a real demo order number and itemized server-side snapshot through the existing order repository. Confirmation displayed the chosen Gold/17 UUID, pending order status and unpaid COD state, not a fake successful-payment claim.
24. **InstaPay result.** The configured InstaPay option explains that staff verify payment. Its placed demo order remained `verification_required`; it was not labelled paid at checkout or after receipt.
25. **Transfer proof.** The shared proof panel accepts a reference/image and submits through the existing repository. A successful demo upload stored proof data while payment stayed awaiting human verification. No new automatic settlement rule was added.
26. **Confirmation truth.** Confirmation renders the returned order/lookup snapshot—reference, items/SKUs, payment/fulfilment, totals and next steps—not totals reconstructed from the current product page. The DOM and Chromium tests waited for the itemized detail, not just the first receipt heading.
27. **Refresh and tab privacy.** A short-lived `sessionStorage` pair holds **reference + phone + timestamp**, never an order body; refresh re-queries with both. A different tab lacking the pair sees a private/track prompt, not another tab's receipt. Receipt URLs never contain the phone.
28. **Private tracking.** A reference by itself reveals no order. The lookup requires the matching phone, keeps the phone out of the hash/query string, provides a not-found response for incorrect credentials and disables repeated submission while loading.
29. **Status and timeline.** Correct reference + phone returns the repository's actual order status, payment status, itemized detail and workflow timeline; no browser-inferred paid, dispatched or delivered state is shown.
30. **Browser-local shopper profile.** Registration/login, profile and persisted session reuse `StoreAccountProvider` and its local account repository in both online modes. This is intentionally **not** a Supabase Auth/staff account or a cross-device customer identity.
31. **Addresses and wishlist.** Account tabs use the shared saved-address and wishlist actions. Guest favourites and signed-in conveniences retain their documented browser-local limits; product cards in the wishlist still read published products.
32. **Private history.** Only references associated with the local shopper account are remembered; history entries are fetched by the existing reference-and-phone-gated repository, including after a new signed-in order or a correctly tracked guest order. The browser test waited for history loading to settle before asserting an order or a genuine empty history.
33. **Valid reorder.** `planV2Reorder()` admits a published, active, stock-tracked simple product as a `null` variant line and an active exact variant **only under its original UUID**. It accounts for held/current cart quantities and cumulative repeated historical lines; all-valid orders continue to the V2 bag.
34. **Refused historical lines.** Missing/unpublished/inactive products, disabled tracking, foreign/inactive/removed or sold-out exact variants, insufficient stock and malformed quantities are excluded. No same-size/sibling-colour substitution occurs; the warning identifies the old item name **and SKU**.
35. **Partial reorder.** When an order combines valid and invalid lines, only the valid original lines are requested from the shared cart. After the cart commits, Orders shows the specific unavailable items, an EN/AR partial-success status, and an explicit V2 bag link; it stays on the warning rather than navigating away. The Chromium fixture ordered a simple product plus Gold/17, deactivated only Gold/17, and observed **only the simple item** in the bag in both languages.
36. **Loading and state-race guard.** Order history can arrive before the catalogue. Reorder buttons now wait for the current catalogue to load (and offer retry on a catalogue error), preventing a premature false-unavailable result. React can also defer the shared cart's state updater, making `addMany()`'s immediate count temporarily zero even when it adds the line; V2 verifies the **committed** cart quantities before displaying success or a refusal.
37. **About.** The V2 About route uses the existing bilingual `WebsiteSettings.about` title, body, image and configured CTA, with a restrained fallback for absent optional content. It does not invent a company story or separate editorial database.
38. **Contact and social.** The V2 Contact page uses configured phone, email, address, map, hours, available zones, InstaPay link and shared social settings. Its message CTA opens a validated WhatsApp compose link if configured; otherwise it explains that no WhatsApp action is available. There is **no fictional on-site message inbox**.

## Acceptance evidence

39. **English/Arabic.** Shared i18n strings cover the new partial-reorder explanation in EN and AR. Chromium exercised both LTR and RTL route layouts, plus exact-SKU warnings and the bag link in both languages. Language selection never changes the persisted variant UUID.
40. **Responsive geometry.** The rendered matrix checked **seven populated Phase 3 routes**—bag, checkout, confirmation, tracking, account, About and Contact—at **320, 360, 375, 390, 414, 430, 768, 1024, 1280, 1440 and 1920 px** in each language: **154/154 route cases**. It checked heading, V2 header actions, content bounds, document/body width and reachable footer; no case scrolled horizontally or clipped the sampled panels. Seventy representative route/language/width screenshots are Git-ignored in `coverage/visual-v2-phase3/`; four phone captures (cart, checkout, receipt, account) were visually reviewed in this pass.
41. **Loading, empty and error states.** A fresh Chromium profile observed a labelled catalogue loading skeleton, zero-result catalogue state with working Clear filters, empty bag with Browse link, empty shopper history, required tracking-field alerts, disabled lookup while pending and private not-found alert. The DOM journey checked checkout validation and saved-cart pruning. The catalogue's retry affordance and Orders' catalogue-error retry are implemented; a production backend outage was **not** simulated.
42. **Practical accessibility.** Chromium checked one main landmark and heading, search semantics, named inputs, product image alt text, mobile filter-dialog Escape, size-guide/lightbox focus return, status/alert roles, disabled invalid choices and no mobile overflow. V2 has a skip link, visible focus styles and Phase 2 reduced-motion handling. This is **not** an automated WCAG audit or accessibility certification; touch-target and assistive-technology coverage remain outside this test's proof.
43. **Focused logic and DOM.** `npm test` passed **48/48 logic suites**; `journey.selftest.ts` passed **9/9** focused tests covering simple/exact reorder, unpublished/inactive/untracked/sold-out and foreign UUIDs, reserved/cart stock, duplicates, partial valid+invalid, no substitution and EN/AR keys. The current `v2-journey` DOM suite passed **29 shopper assertions** across COD, InstaPay, proof, coupons, delivery estimates, private tracking, local account and legacy isolation. Its delivery estimate was allowed to settle before comparison with the order snapshot.
44. **Rendered, regression and static checks.** The final Chromium suite passed **154/154** route cases plus the separate PDP/filter/receipt/privacy/state/partial-reorder flows; it was repeated on the final app build and passed twice. `npm run test:e2e` passed **25/25 currently registered suites**, including older storefront, POS, Admin and Phase 1–2 regressions. `npm run typecheck`, `npm run build` and `git diff --check` passed. `npm run lint` exited successfully with **0 errors and 32 warnings across the worktree**; it was **not** warning-free, and its output listed no warning in this final pass's Phase 3 source/test files. The registered report suite uses an isolated in-memory test database; no production database action is implied by its pass.

## SQL, provenance and stop line

45. **Dirty SQL classification — C (attribution unprovable).** At the start of this pass `supabase/tests/scenarios.sql` was already modified and `supabase/migrations/0061_last_active_variant_guard.sql` was already untracked. Read-only inspection shows variant archive/delete permission and last-active-shelf tests; `src/modules/operations/types.ts` also refers to 0061. Local Git status, timestamps and available commit history do **not** prove who authored these uncommitted changes, so classification **A** cannot be asserted. Phase 3's V2 reorder/checkout relies on existing published reads and order repositories; it does **not** require this guard migration, so **B** is not supported either. Both SQL files remain untouched; no SQL file was applied to a project or live database, no scenario SQL was invoked directly, and no RLS/RPC edit, deployment or production DB change was performed for this pass. The registered E2E report suite's isolated in-memory SQL tests are accounted for in point 44.
46. **Limits and next approval.** The completed **local Phase 3** is still an opt-in, demo-validated shopper journey. Live Supabase anonymous reads/order placement, payment operations, production error recovery and formal accessibility conformance were not certified. The legacy `#/store` route, Phase 2 settings/social/WhatsApp behaviour and POS/Admin were preserved; Phase 4, canonical switch, deployment, production orders, database work and GitHub publication were **not** undertaken. Any rollout or live-schema decision needs a separate, explicit authorization and live-environment validation.
