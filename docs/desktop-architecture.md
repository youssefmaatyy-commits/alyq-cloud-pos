# Desktop shell architecture decision

Status: accepted for Prompt 5

Primary target: Windows x64

## Decision

ALYQ uses **Electron** as a thin, hardened shell around the existing React/Vite application. The web and desktop products load the same `src/` application, use the same Supabase project, and execute the same POS, stock, promotions, shift, permissions, audit, offline/outbox, receipt and sync code. Native behavior is available only through `src/lib/desktop/bridge.ts`.

This is not a second POS and it is not a second backend.

## Why Electron, not Tauri, for this repository

The choice is based on compatibility and operational risk rather than framework popularity.

| Concern | Electron | Tauri in this repository |
| --- | --- | --- |
| Existing build | Loads the current single-file Vite output directly; HashRouter needs no rewrite | Also capable of loading Vite output, but requires a new Rust build/toolchain |
| Windows printing | Chromium/Electron exposes installed printer enumeration and a controlled print-spool API | Printing needs a Rust/plugin/native path whose Windows behavior and maintenance would have to be introduced and validated |
| Hardware bridge | Small preload/main-process allowlist in JavaScript; keyboard-wedge scanners remain in the shared renderer | A Rust command layer and plugin selection would be required for the same adapter boundary |
| Build reproducibility | Pinned npm lockfile and `electron-builder`; same Node toolchain already used by the repository | Rust/Cargo and target toolchains are not part of the repository or the current build environment |
| Security | Mature context isolation, sandboxing and navigation controls, provided the IPC surface stays narrow | Smaller default webview footprint, but safety would depend on new Rust commands/plugin permissions that this team cannot currently compile here |
| Footprint | Larger installer/runtime because Chromium is bundled | Usually smaller, an advantage, but not enough to outweigh unvalidated printing/toolchain risk for a till |

Tauri's smaller footprint is real. It does not compensate for adding an unproven Windows printing/plugin and Rust release chain to a repository that currently has neither. Electron is therefore the lower-risk compatible shell for this implementation.

## Trust boundaries

- The renderer has no Node integration and cannot import Electron.
- `contextIsolation`, Chromium sandboxing and web security are enabled.
- The preload exposes named, typed operations only. It exposes no arbitrary IPC, filesystem, process, shell, network or printer options.
- Main-process IPC verifies that the sender is the main frame of the one ALYQ window and validates all values again.
- Navigation remains inside the packaged `index.html` (or an explicitly local development origin). New windows are denied. Only validated HTTP(S) links with no embedded credentials may be handed to the operating system.
- Webviews and all browser permission requests are denied.
- Printable HTML runs in a hidden, sandboxed, JavaScript-disabled window with an injected restrictive CSP. The configured printer and paper size come from main-process configuration, not receipt input.
- Cash-drawer jobs are rate-limited and use only the configured printer-driver mode. The renderer cannot supply a process, command, path, printer name or raw ESC/POS bytes.
- Register credentials are generated by the backend and stored in Electron's per-user data directory with restrictive file permissions where supported. Renderer-wide configuration is credential-redacted; only the narrow register RPC adapter can request the binding proof needed for authenticated Supabase calls. Credentials are not built into the app, localStorage, IndexedDB, diagnostics or receipts.
- Packaged renderer responses receive a restrictive content-security policy. A fixed-channel native full-screen event is the only inbound preload subscription and can only originate in the main process.

## Printing and drawer truthfulness

A successful Electron print callback means **submitted to the operating-system print spooler**. It does not prove that paper emerged, that the cover is closed, or that the drawer opened. UI and diagnostics must say “submitted” or “Unknown”, never “printed” or “healthy”, unless a future device adapter can prove that state.

The initial cash-drawer path is the widely supported printer-driver workflow: the configured Windows printer driver is responsible for opening its attached drawer for a dedicated tiny print job. A drawer command is sent only after a completed cash transaction or after an authoritative manual-open authorization. Card/InstaPay transactions never trigger it. Sites whose driver cannot map a dedicated job to a drawer pulse must leave drawer mode disabled; ALYQ does not execute PowerShell, arbitrary shell commands or unreviewed vendor SDKs as a workaround.

Print/drawer outcomes are operational side effects. They never commit, retry, void, reverse or mutate a sale. Historical receipt HTML is always rebuilt from frozen sale evidence and reprinting never invokes pricing or sale completion.

## Persistence and lifecycle

Electron loads the packaged app from a stable `file://` origin, so the existing IndexedDB database and outbox remain under one persistent Chromium profile in `app.getPath("userData")`. Closing, restarting or updating the shell does not clear that profile. The close warning reports pending/conflicted operations but explicitly permits a safe close because durable operations must survive it.

Installer uninstall settings do not remove application data by default. Catalog cache repair remains separate from durable business stores.

## Updates and signing

This change is **update-ready**, not an insecure auto-updater:

- package identity and version are stable;
- installer output is reproducible from the pinned lockfile and package scripts;
- build/SHA facts are exposed to the application;
- generated output stays outside Git.

No update URL, signing certificate or release trust chain exists in this repository, so no auto-update code is enabled. Production distribution must add a protected CI release job, Windows code-signing certificate custody, signed installer and update metadata, TLS release hosting, staged rollout/rollback and signature verification before an updater is switched on.
